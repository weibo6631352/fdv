# 二次开发排产计划

## 1. 排产目标

本计划的目标不是解释架构，而是把开发工作切成可以由多个 agent 并行推进、且冲突最小的工作流。

排产原则只有四条：

- 高冲突文件必须单人独占
- 新增目录优先独立分配
- 先冻结契约，再并行开发
- 平台整合放到最后合并

本次推荐采用 **4 个开发 agent + 1 个协调 / 集成 agent** 的编制。

## 2. 编组方案

### Agent 0：协调 / 集成

职责：

- 维护主分支集成顺序
- 冻结接口版本
- 处理跨 agent 冲突
- 审查合并顺序
- 做最终集成和 smoke check

只负责协调与集成，不承担大块功能开发。

### Agent 1：Strategy API 与装配骨架

职责：

- 新建 `strategy_api/`
- 定义核心模型和接口
- 定义策略加载器
- 定义最小策略装配约定
- 补最基础的接口测试

### Agent 2：默认 FDV 策略迁移

职责：

- 把当前 FDV 逻辑迁入 `strategies/current/`
- 保持现有行为等价
- 为默认策略补本地回归样例

### Agent 3：平台整合

职责：

- 改造 `MarketService`
- 改造 `StrategyService`
- 改造 `StrategyWorker`
- 改造 `ReconcileService`
- 改造 `main.py` 装配逻辑

### Agent 4：配置 / 测试 / replay / 文档

职责：

- 策略配置形态
- `tests/strategies/`
- replay 工具
- 二次开发文档

## 4. 并行开发顺序

### 4.1 先完成 Agent 1

Agent 1 的输出是其他 agent 的共同依赖。它先交付以下内容：

- `StrategySpec`
- `StrategyContext`
- `StrategyDecision`
- `RecoveryDecision`
- `StrategyModule`
- 最小装配约定

只有这些接口和命名冻结后，其余 agent 才开始长期开发。

### 4.2 Agent 2、Agent 3、Agent 4 并行

在 Agent 1 完成后，以下三条线并行：

- Agent 2：默认策略迁移
- Agent 3：平台整合
- Agent 4：测试、replay、文档

并行时的依赖关系如下：

- Agent 2 依赖 Agent 1 的接口定义
- Agent 3 依赖 Agent 1 的接口定义
- Agent 4 依赖 Agent 1 的接口定义
- Agent 4 的契约测试可以先行，不必等待 Agent 2 完成
- Agent 3 可先接入 stub/default strategy，再在后续切换到 Agent 2 的真实实现

### 4.3 Agent 0 负责集成

Agent 0 不等待所有人都写完再收口，而是按下面顺序集成：

1. 合并 Agent 1
2. 合并 Agent 2
3. 合并 Agent 4
4. 合并 Agent 3

这么排的原因是：

- Agent 1 是公共基础
- Agent 2 先把默认策略落地，Agent 3 才能对真实策略做平台接线
- Agent 4 基本写新增目录，冲突低，适合中间快速落
- Agent 3 改动核心平台文件最多，应最后合并并统一处理冲突

## 6. 合并与联调规则

### 6.1 合并规则

- 不允许两个 agent 同时长期改同一个高冲突文件
- 共享接口命名只由 Agent 1 定版
- `main.py` 只允许 Agent 3 修改
- `docs/README.md` 只允许 Agent 4 修改
- 每个 agent 在提交前都必须 rebase 到最新集成分支

### 6.2 联调规则

联调只做三件事：

- 平台装配能启动
- 当前策略能通过主链路走通
- 当前策略能通过契约测试和 replay

联调责任归 Agent 0 和 Agent 3，Agent 2、Agent 4 配合修本线问题。

## 7. 推荐工作方式

推荐按下面方式并行：

### 第一天

- Agent 0：建立集成分支、冻结接口命名
- Agent 1：完成 `strategy_api/` 骨架

### 第二天开始

- Agent 2：迁移当前 FDV 策略
- Agent 3：改造平台调用链
- Agent 4：测试、replay、文档同步推进

### 平台合流窗口

- Agent 0 每天固定一次拉齐接口变化
- Agent 3 在 Agent 2 的当前策略落地后切换真实接线
- Agent 4 在接口稳定后补指南，不追着平台代码改

## 8. 最优并行切法

这次改造最优切法不是按“模块目录”平均分，而是按“冲突热度 + 依赖中心”切：

- 把所有公共契约集中给 Agent 1
- 把当前策略迁移集中给 Agent 2
- 把平台整合集中给 Agent 3
- 把测试、工具、文档集中给 Agent 4
- 用 Agent 0 做持续集成和冲突消解

这样切的好处是：

- 新目录多，天然适合并行
- 高冲突文件少，且有明确 owner
- 平台改造最后合并，减少返工
- 真实二次开发体验不会被拖到最后才补

## 9. 结论

本次排产建议采用：

- 1 个协调 / 集成 agent
- 4 个开发 agent
- 先冻结 `strategy_api`
- 再并行推进当前策略、平台整合、测试工具文档
- 最后由平台整合线收口主链路

这是一种冲突最小、并行度高、且最适合当前仓库改造目标的分工方式。
