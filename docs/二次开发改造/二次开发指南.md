# 二次开发指南

这份指南只讲最终做法。

## 1. 改哪里

不要去平台层到处改交易规则。

固定策略入口是：

- `src/fdv_trader/strategies/current/strategy.py`
- `src/fdv_trader/strategies/current/config.py`

参考实现：

- `src/fdv_trader/strategies/fdv_default/`

模板：

- `src/fdv_trader/strategies/template/`

## 2. 推荐开始方式

1. 先看 `template/strategy.py`
2. 把你需要的筛选、分配、入场、退出、恢复逻辑写进 `current/strategy.py`
3. 把策略参数写进 `current/config.py`
4. 如果参数较多，单独放到 `.json` 或 `.toml`
5. 用 `STRATEGY_CONFIG_PATH` 指向这份结构化配置

单策略项目里，`current/` 就是实际运行入口。

## 3. 不要改的地方

二次开发时，下面这些默认不要改：

- `runtime/`
- `workers/`
- `infra/polymarket/`
- `app/trading_service.py`
- 风控和执行链路

只有当你的策略能力明确要求平台新增通用能力时，才去改平台层。

## 4. 本地验证顺序

先跑契约测试：

```bash
pytest tests/strategies/contract
```

再跑 replay：

```bash
fdv-trader replay --fixture tests/strategies/fixtures/entry_replay.json
```

如果 replay 没输出 `ready_to_trade=true`，先修策略，不要急着起整套 runtime。

最后再跑全量测试：

```bash
pytest
```

## 5. 配置建议

策略参数优先放结构化文件，不要继续往环境变量里无限堆。

当前支持：

- `.json`
- `.toml`

示例：

```bash
STRATEGY_CONFIG_PATH=./strategy.toml
```

## 6. 开发交付最低要求

一个新的二次开发策略，至少要同时交付：

- `current/strategy.py`
- `current/config.py`
- 一份结构化配置样例
- 契约测试通过
- replay 样例通过

## 7. 判断是否需要平台改造

只有出现下面这些情况，才值得动平台层：

- 现有 `StrategyContext` 拿不到必要状态
- 现有 `EntrySizing` / `StrategyDecision` 表达不了你的策略结果
- replay 和契约测试无法覆盖你的策略主语义

除此之外，优先把变化控制在 `strategies/current/`。
