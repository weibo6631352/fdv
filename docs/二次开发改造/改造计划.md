# 二次开发改造计划

## 1. 改造目标

本次改造的目标，是把当前仓库升级为一个适合二次开发的单策略交易底座。

目标状态如下：

- 单个 runtime 只运行一个策略实现。
- 策略作者可以直接围绕稳定接口编码，不需要改动执行、风控、WebSocket、数据库和审计底座。
- 允许为了长期质量进行合理架构调整，不受“尽量少改”限制。
- 平台层统一负责执行安全、风控门禁、恢复修复、审计落库和运行时治理。
- 当前 FDV 策略收敛为第一套内置策略实现，作为默认策略和模板参考。

## 2. 改造边界

本次改造明确采用以下边界：

- 不做多机器人平台。
- 不做多策略并行运行。
- 不做插件市场、远程热插拔、在线脚本执行。
- 不允许策略绕过 `TradingService -> RiskManager -> Order Executor`。
- 不继续把具体策略语义散落在平台层多个模块里。

## 3. 总体方案

项目重构为两层：

- 平台层：运行时、状态、执行、风控、恢复、审计、配置、装配
- 策略层：universe、入场、仓位、退出、恢复目标

平台层不再承载具体策略语义；策略层不再接触执行通道。

整体方向不是做成一个“什么都支持”的大框架，而是做成一个：

- 单 runtime
- 单策略运行时
- 高质量策略接口
- 高可维护平台底座

## 4. 平台层与策略层职责

### 4.1 平台层职责

平台层负责：

- 市场与账户快照维护
- 事件总线与 worker 调度
- 下单、撤单、改价执行
- 风控检查
- supervisor、暂停与恢复控制
- 审计、trace、outbox、持久化
- 策略加载与装配

平台层继续复用和演进的核心模块包括：

- [main.py](/home/wangwb/code/fdv/src/fdv_trader/main.py)
- [runtime](/home/wangwb/code/fdv/src/fdv_trader/runtime/README.md)
- [trading_service.py](/home/wangwb/code/fdv/src/fdv_trader/app/trading_service.py)
- [risk.py](/home/wangwb/code/fdv/src/fdv_trader/domain/risk.py)
- `infra` 下的执行与外部适配模块

### 4.2 策略层职责

策略层只负责回答五个问题：

- 哪些 market 进入当前策略 universe
- 何时产生入场机会
- 买多少
- 如何退出
- 恢复阶段应维持什么订单覆盖状态

策略层不提交订单，不直接访问数据库，不直接访问外部网络。

## 5. Strategy API

本次改造的核心，是建立稳定的 Strategy API。

### 5.1 核心模型

建议新增 `strategy_api/`，定义以下核心模型：

- `StrategySpec`
  - 策略名称
  - 版本
  - 描述
  - 配置模型
  - 能力声明

- `StrategyContext`
  - `Market`
  - `OrderbookSnapshot`
  - `AccountSnapshot`
  - `Position`
  - `open_orders`
  - trace、时钟、运行态信息

- `StrategyDecision`
  - `skip`
  - `buy`
  - `sell`
  - `cancel`
  - `replace`
  - 每种决策都必须带原因和必要参数

- `RecoveryDecision`
  - 应维持的订单覆盖
  - 是否取消多余订单
  - 是否改价
  - 是否暂停 market

### 5.2 职责接口

策略模块建议包含以下职责对象：

- `UniverseSelector`
- `EntryPolicy`
- `SizingPolicy`
- `ExitPolicy`
- `RecoveryPolicy`

实现上可以通过一个 `StrategyModule` 聚合暴露这些能力，对平台保持一个稳定入口。

### 5.3 接口约束

Strategy API 必须满足：

- 不依赖 FastAPI、SQLAlchemy、WebSocket client、交易所 SDK
- 输入只使用内部 DTO 或纯 Python 类型
- 输出必须可审计、可测试、可回放
- 所有拒绝、跳过、修复原因都必须明确

## 6. 关键架构调整

### 6.1 `MarketService`

当前 `MarketService` 默认耦合固定分类器。改造后应拆成两段：

- 平台解析：把原始 payload 转为内部 market 对象
- 策略筛选：由 `UniverseSelector` 决定是否纳入当前策略 universe

这样平台只负责“解析”，策略负责“筛选”。

### 6.2 `StrategyService`

`StrategyService` 改为策略调用桥。

它负责：

- 构造 `StrategyContext`
- 调用当前策略实现
- 将 `StrategyDecision` 转为统一平台动作

它不再负责写死：

- 固定入场价
- 固定卖出价
- 固定等权分配
- 固定 FDV / 500M 语义

### 6.3 `StrategyWorker`

`StrategyWorker` 继续保留为平台 worker，但只消费平台事件并调用 `StrategyService`。

它不再承载具体策略规则，只负责：

- 接收事件
- 取快照
- 调用策略
- 将策略结果送入平台执行链路

### 6.4 `ReconcileService`

`ReconcileService` 不再内置固定卖出修复逻辑，而是根据 `RecoveryPolicy` 生成恢复目标。

它负责：

- 读取账户与 market 状态
- 调用策略恢复语义
- 生成修复动作
- 仍通过统一执行链路执行

### 6.5 `main.py`

`main.py` 改为单策略装配入口。

它负责：

- 加载平台配置
- 加载固定策略入口
- 加载策略配置
- 组装 `MarketService`、`StrategyService`、`ReconcileService`、workers

运行时不再直接写死 FDV 策略 wiring。

## 8. 默认策略处理方式

当前 FDV 策略不再作为平台默认散落逻辑存在，而是迁入：

- `strategies/fdv_default/strategy.py`
- `strategies/fdv_default/config.py`

其职责包括：

- 当前 FDV universe 过滤
- 当前入场逻辑
- 当前资金分配逻辑
- 当前退出逻辑
- 当前恢复目标定义

默认策略迁入后，平台仍然只知道“当前策略实现”，不再知道“FDV 是特殊策略”。

## 9. 配置方案

配置拆成两层：

- 平台配置
  - 数据库、执行、WS、超时、线程池、运行时控制
- 策略配置
  - 当前策略的专属参数

建议新增：

- `STRATEGY_CONFIG_PATH=...` 或等价方式

策略复杂参数优先使用结构化配置文件，不继续无节制堆积环境变量。

## 10. 二次开发支持

如果要让工程师方便编码定制策略，下面这些不是附属项，而是方案的一部分：

- 提供 `strategies/template/`
- 提供稳定的策略契约测试
- 提供最小 replay 能力
- 提供一份清晰的 `二次开发指南.md`

策略开发者的理想工作方式应是：

1. 复制模板策略目录
2. 将实现收口到 `strategies/current/`
3. 修改策略代码和配置
4. 运行契约测试与 replay
5. 用固定入口启动 runtime
6. 在不动平台底座的前提下运行新策略

## 11. 需要落实的改造内容

本次改造直接按以下内容落地：

1. 新建 `strategy_api/`
2. 新建 `strategies/`
3. 收口当前 FDV 逻辑到 `strategies/fdv_default/`
4. 重写 `StrategyService` 为策略桥接层
5. 改造 `MarketService` 为“平台解析 + 策略筛选”
6. 改造 `StrategyWorker` 为纯平台 worker
7. 改造 `ReconcileService` 接入 `RecoveryPolicy`
8. 在 `main.py` 中加入单策略装配
9. 增加策略契约测试与 replay
10. 增加模板策略与二次开发文档

## 12. 最终形态

改造完成后，项目应呈现为以下形态：

- 平台层稳定、统一、负责安全执行
- 策略层独立、清晰、便于编码
- 单 runtime 只装载一个策略实现
- 默认 FDV 策略是一个普通内置策略，而不是平台特殊分支
- 新策略开发成为“写一个策略模块”，而不是“到处改系统源码”

## 13. 结论

本次改造的核心，不是把项目做大，而是把项目做对。

方向应当明确：

- 不做多机器人
- 不做伪通用框架
- 做高质量单策略底座
- 做稳定 Strategy API
- 做真正可用的二次开发体验

这套方案的落点，就是让工程师以后开发新策略时，主要工作发生在 `strategies/<name>/` 和策略配置上，而不是继续深入平台底层反复拆旧逻辑。
