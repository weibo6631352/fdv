# 交易框架需求文档

本文档只定义框架需求，不定义某个具体策略的选市场、定价和持仓规则。

策略相关规则属于策略实现，当前示例策略放在 `src/strategies/current/`。框架契约以 `src/polymarket_trader/extension_api/` 为准。

## 1. 目标

框架需要提供一套可复用的 Polymarket 交易运行时，支持：

- 发现市场并维护本地市场索引。
- 订阅 market / user 实时数据并维护内存状态。
- 将策略决策转换成统一订单意图。
- 统一执行下单、撤单、改价和恢复动作。
- 提供审计、持久化、管理接口和状态校准能力。
- 让二次开发人员主要在少量策略文件内实现业务，不必改动框架主链路。

## 2. 范围

框架负责：

- 运行时装配与生命周期管理。
- WebSocket、REST、数据库、队列、线程池、进程池等基础设施。
- 市场、订单簿、订单、成交、持仓、资金、审计等通用模型。
- worker 调度、事件总线、持久化和 Admin API。
- 业务扩展接口与扩展上下文对象。

框架不负责：

- 某个策略的 discovery 关键词。
- 某个策略的市场筛选语义。
- 某个策略的入场价格、退出价格、资金分配细则。
- 某个策略是否保留已被过滤市场的订阅。

这些都应由策略模块决定。

## 3. 业务扩展接口需求

框架必须提供稳定的业务扩展接口，至少包含以下能力：

- 市场是否纳入业务扩展 universe 的判断。
- 入场资金分配。
- 入场决策。
- 退出决策。
- 恢复决策。

当前代码中的接口位置：

- `src/polymarket_trader/extension_api/hooks.py`
- `src/polymarket_trader/extension_api/context.py`
- `src/polymarket_trader/extension_api/decisions.py`
- `src/polymarket_trader/extension_api/ports.py`
- `src/polymarket_trader/extension_api/manifest.py`

业务扩展模块输出的应当是框架定义的决策对象，而不是直接调用交易客户端。

## 4. 运行时需求

框架必须能在一个进程内装配以下组件：

- `GammaClient`
- `ClobClient`
- `DataClient`
- `PolymarketWebSocketClient`
- `EventBus`
- `MarketRegistry`
- `AccountStateStore`
- `LocalOutbox`
- `PersistenceWorker`
- `MarketDiscoveryWorker`
- `MarketWsWorker`
- `UserWsWorker`
- `TradingDecisionWorker`
- `ReconcileWorker`
- `AdminService`

当前装配入口：

- `src/polymarket_trader/main.py`

要求：

- 启动时完成配置校验。
- 恢复本地可恢复状态后，再进行权威快照校准。
- 未完成初始校准前，不允许自动交易。
- 关闭时按顺序停止后台任务并释放资源。

## 5. 状态管理需求

框架必须维护统一的内存状态，至少包括：

- market registry
- orderbook snapshot
- account balance / allowance
- positions
- open orders
- fills
- readiness / runtime snapshot

状态要求：

- 交易判断优先使用内存状态。
- 权威状态来源仍然是 Polymarket 实时流和快照接口。
- PostgreSQL 只用于审计、复盘、查询和恢复参考，不作为交易唯一真相来源。

## 6. 数据接入需求

框架必须支持以下数据接入方式：

- Gamma API：发现 event / market 元数据。
- CLOB Market WS：接收盘口、价格和 market 状态变化。
- CLOB / Data / User 侧接口：接收订单、成交、持仓和账户相关状态。
- REST fallback：在 WS 丢失、重连或校准时拉取权威快照。

要求：

- WebSocket 断线必须自动重连。
- 重连后必须执行状态校准。
- 订阅管理由框架维护，策略通过接口间接影响订阅范围。

## 7. 订单执行需求

框架必须统一处理以下动作：

- BUY
- SELL
- CANCEL
- REPLACE

要求：

- 只有统一的交易执行链路可以真正下单、撤单、改价。
- HTTP handler、worker 和策略模块都不能绕过执行器直接调用交易客户端。
- 订单执行必须产生可审计结果。
- 同步阻塞调用必须离开交易主事件循环。

## 8. 恢复与校准需求

框架必须提供 reconcile 能力，用于：

- 校准 market 状态。
- 校准 orderbook 状态。
- 校准 open orders、fills、positions。
- 处理异常挂单、缺失挂单和状态漂移。

要求：

- reconcile 可以由调度器自动触发，也可以由 Admin API 人工触发。
- 恢复动作是否取消、补挂、暂停 market，应由策略恢复决策决定。

## 9. 持久化与审计需求

框架必须支持异步持久化，至少包括：

- markets
- orderbook snapshots
- orders
- fills
- positions
- allocations
- audit events
- outbox events
- account snapshots

要求：

- 持久化失败不能直接阻塞交易主链路。
- 审计记录需要保留 trace_id、事件标题、订单和成交关联字段。
- 管理查询优先从仓储快照读取；没有数据库时，按接口定义回退到运行时快照或空分页。

## 10. Admin API 需求

框架必须提供受控管理接口，用于：

- 健康检查。
- readiness / runtime / workers / metrics 查询。
- markets / orders / fills / positions / portfolio 查询。
- allocations / audit-events / outbox 查询。
- 手动 reconcile。
- 人工 replace open order。

接口契约文档：

- `docs/api.md`

要求：

- Admin API 只做参数校验、调用应用服务和序列化响应。
- Admin API 不是策略计算入口，也不是交易客户端直连入口。

## 11. 配置需求

框架配置原则：

- `.env` 只放框架运行参数。
- 策略参数不作为框架必填环境变量。
- 策略参数写在策略包内，或通过策略自己的配置加载方式处理。

框架运行参数至少包括：

- Polymarket host / WS 地址
- 钱包与交易客户端参数
- 数据库连接
- 线程池 / 进程池 / 队列大小
- 超时、重试和风控上限
- 调度周期

## 12. 非功能需求

### 12.1 性能

- 交易主链路优先级最高。
- 后台扫描、数据库写入、日志和管理查询不能反向阻塞交易主链路。
- 队列必须有容量上限和指标。

### 12.2 可维护性

- 二次开发优先改策略模块，不要先改框架主链路。
- 通用能力进框架，策略差异进策略目录。
- 契约字段命名必须单义，不能出现一套名字对外、一套名字对内的长期兼容层。

### 12.3 可观测性

- 关键路径必须有 trace_id。
- 需要暴露运行时快照、worker 状态和关键延迟指标。
- 审计事件必须能串起 discovery、判断、下单、成交和恢复流程。

## 13. 开发入口

框架开发常看这些文件：

- 运行时装配：`src/polymarket_trader/main.py`
- 应用服务：`src/polymarket_trader/app/`
- 领域模型：`src/polymarket_trader/domain/`
- 扩展接口：`src/polymarket_trader/extension_api/`
- worker：`src/polymarket_trader/workers/`
- 管理接口：`src/polymarket_trader/api/`
- 当前示例扩展：`src/strategies/current/`

## 14. 验收口径

框架层至少满足以下标准：

- 可以在不修改交易主链路的前提下替换策略模块。
- 可以稳定维护市场、订单、成交、持仓和资金状态。
- 可以通过 Admin API 查询关键运行态并触发受控操作。
- 可以在数据库不可用或暂时不可用时维持核心交易流程。
- 可以在 WebSocket 重连后完成状态校准并恢复运行。
