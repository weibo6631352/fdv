# Polymarket FDV 自动交易系统需求文档

参考链接：
- https://polymarket.com/
- https://docs.polymarket.com/

## 1. 目标

构建一个 Polymarket 自动化交易系统，用于实时发现 Crypto 分类下、名称包含 FDV 与 500M 信息的 markets，并在满足价格、流动性、组合资金分配和风控条件时买入 `NO outcome token`。

系统采用多市场组合策略，不对单个 market 重仓。资金需要在筛选出的多个目标 markets 之间尽量平均分配；如果某个 market 当前买不满预算，未使用资金立即释放，并分配给其他仍可买入的 eligible markets。

交易执行规则：
- 买入侧不使用会长期停留在 orderbook 中的 resting BUY limit order。
- 只有当 `NO best ask <= 0.60` 时，才提交价格上限为 `0.60` 的 `FAK BUY order`。
- `FAK`（Fill-And-Kill）买单立即成交可用部分，并自动取消未成交剩余部分，避免资金被长期占用。
- 买入成交后，对已成交数量提交 `GTC SELL limit order at 0.70`。
- 卖出单一直挂着，直到成交、market 不再可交易、系统风控取消或人工取消。

## 2. 核心策略

策略假设：
- 新币种或新项目在指定时间内达到 `FDV >= $500M` 是低概率事件。
- 当相关 market 的 `NO outcome token` 可在 `0.60` 或更低价格买入时，策略认为具备进入价值。
- 通过批量交易多个同类 FDV markets，让单个 market 的意外信息、异常结算或项目特殊情况被组合概率平摊。
- 组合收益依赖长期分散执行、价格纪律和仓位控制，不依赖单个 market 重仓获利。

交易方向：
- 买入标的：目标 market 的 `NO outcome token`
- 买入价格上限：`0.60`
- 买入订单类型：`FAK BUY order`
- 卖出价格：`0.70`
- 卖出订单类型：`GTC SELL limit order`

## 3. Polymarket 术语

- `event`：Polymarket 中的一组相关 markets。
- `market`：具体可交易的预测问题，通常包含 YES / NO outcomes。
- `outcome token`：可交易的结果 token，例如 `YES outcome token` 和 `NO outcome token`。
- `NO token_id`：目标 market 中 NO outcome 对应的 token id，是实际下单使用的交易标的。
- `CLOB`：Central Limit Order Book，Polymarket 的中央限价订单簿。
- `best ask`：买入某个 outcome token 时可立即成交的最低卖价。
- `best bid`：卖出某个 outcome token 时可立即成交的最高买价。
- `spread`：`best ask - best bid`。
- `FAK`：Fill-And-Kill，立即成交可用数量，并取消剩余未成交数量。
- `GTC`：Good-Til-Cancelled，订单一直有效，直到成交、取消或 market 不再可交易。
- `open order` / `resting order`：已经提交并停留在 orderbook 中等待成交的订单。

## 4. 市场筛选

系统只处理 Polymarket 中满足基础交易条件的 Crypto 分类 markets：
- `active = true`
- `closed = false`
- `enableOrderBook = true`
- 未 resolved / cancelled / archived
- 支持 CLOB 交易
- 能够获取 `conditionId`、`market slug`、`YES token_id`、`NO token_id`、`tick_size`、`min_order_size`
- event 或 market 的 category / tag 必须包含 Crypto / Cryptocurrency 等加密货币分类；Pre-Market 可以作为附加标签，但不能替代 Crypto 分类

Crypto 分类是必选过滤条件。只有满足 Crypto 分类要求后，才继续做 FDV 与 500M 文本匹配。

文本匹配字段：
- `event title`
- `market question`
- `market slug`
- `market description`
- tag / category 文本

筛选规则：
- event 或 market 必须属于 Crypto / Cryptocurrency 等加密货币分类；Pre-Market 只作为附加标签，不作为 Crypto 分类的替代条件。
- `event title` 必须包含 FDV 相关信息，例如 `FDV` 或 `fully diluted valuation`。
- 在该 event 下，目标 market 的 `market question`、名称或 `market slug` 必须包含 500M 相关信息，例如 `$500M`、`500M`、`500 million`。
- 如果同一 event 下存在多个阈值 markets，只交易 500M 阈值 market。
- 不交易 `$150M`、`$300M`、`$800M`、`$1B` 等其他阈值 markets。
- 不使用宽泛的 `valuation` 关键词作为独立命中条件，避免误匹配普通估值类 markets。
- 不额外通过外部数据判断 token 上线时间、symbol 或项目背景；“新币”判断只基于 Polymarket event / market 文本。

target market 必须同时满足：
- 分类条件：属于 Crypto / Cryptocurrency 等加密货币分类。
- FDV 条件：`event title` 包含 FDV 相关信息。
- 500M 条件：目标 market 的名称、问题文本或 `market slug` 包含 500M 相关信息。
- 交易条件：active、open、CLOB enabled，且能够获取 `NO token_id`。

去重键：
- 优先使用 `conditionId`
- 辅助使用 `market slug`
- 对 outcome 交易使用 `NO token_id`

## 5. 实时数据

系统需要实时获取新 market 和价格更新。

Market 数据：
- 实时订阅 Polymarket 新增 `event` / `market` 数据。
- 发现 Crypto 分类下的 FDV 相关 event 后，立即筛选其中 500M 阈值的 target market。
- target market 进入候选池后，记录发现时间、market 基础信息、匹配字段、匹配关键词和来源响应摘要。

Orderbook 数据：
- 对命中的 target market 订阅 CLOB market channel。
- 实时监听 `NO token_id` 的 orderbook、best bid、best ask、spread、trade、price change。
- 当 `NO best ask <= 0.60` 时触发买入判断。

账户数据：
- 订阅 user channel 或等价账户数据源。
- 实时监听 order、fill、cancel、position 更新。
- 需要同步钱包余额、USDC.e 余额、outcome token 持仓、open orders 和历史成交。

状态校准：
- WebSocket 或实时订阅断线后必须自动重连。
- 重连后使用 REST API 拉取 market、orderbook、orders、fills、positions 快照校准本地状态。
- 本地状态以“实时事件 + 定期快照校准”的方式维护，避免丢消息导致仓位或订单状态错误。

## 6. 买入逻辑

系统只在满足以下条件时提交买入订单：
- market 满足 Crypto 分类、FDV、500M 筛选规则。
- market 满足 active、open、CLOB enabled 等基础交易条件。
- `NO best ask <= 0.60`。
- 买入价格符合该 market 的 `tick_size`。
- 可成交金额满足 `min_order_size`。
- 当前 market 未达到单 market 风险上限。
- 当前策略未达到总投资上限。
- 组合资金分配后，该 market 仍有可买额度。

买入订单规则：
- order side：`BUY`
- token：`NO token_id`
- order type：`FAK`
- price：`0.60`
- size：按该 market 当前可用预算、orderbook 可成交深度、`max_order_usdc` 和 `min_order_size` 计算
- `post-only = false`

执行结果处理：
- full fill：全部成交，立即进入卖出挂单流程。
- partial fill：只对已成交数量进入卖出挂单流程；未成交买入数量由 `FAK` 自动取消，资金立即释放。
- no fill：没有成交时，释放全部买入预算，并重新进入组合资金分配。
- rejected / failed：记录失败原因和原始响应，不无限重试。
- resting BUY 异常：买入侧不允许出现长期 `open BUY order`；如果 API 返回买入订单进入 resting 状态，系统必须立即 cancel 并记录异常。

## 7. 卖出逻辑

买入 `NO outcome token` 成交后，系统对已成交数量提交卖出订单：
- order side：`SELL`
- token：`NO token_id`
- order type：`GTC`
- price：`0.70`
- size：已成交的 NO outcome token 数量

卖出订单规则：
- `SELL limit order at 0.70` 一直保留，直到成交、market 关闭/结算、系统风控取消或人工取消。
- partial fill 后，剩余未成交卖出数量继续作为 `open SELL order` 保留。
- 如果需要改价，系统执行 cancel + replace：先取消原 `open SELL order`，再按新价格提交新的 `SELL limit order`。
- 系统需要支持按 market 查询并操作本账户在同一 `NO token_id` 下的所有 `open SELL orders`。

## 8. 组合资金分配

资金分配采用 `equal_weight` 策略，并允许将未成交或买不满的资金分配给其他仍可买入的 markets。

核心参数：
- `portfolio_budget_usdc`：策略组合总资金预算。
- `eligible_market_count`：当前同时满足 Crypto 分类、FDV / 500M 筛选、价格和风控条件的可买 markets 数量。
- `target_market_budget_usdc = portfolio_budget_usdc / eligible_market_count`。
- `max_order_usdc`：单笔订单 USDC.e 上限。
- `max_market_usdc`：单个 market 总投入硬上限。
- `max_total_usdc`：策略总投资上限。

分配规则：
- 每个 market 的目标投入不超过 `target_market_budget_usdc`，同时不得超过 `max_market_usdc`。
- 单笔订单不得超过 `max_order_usdc`。
- 单个 market 的实际敞口需要统计已成交持仓、pending BUY orders 和 open SELL orders。
- 买入侧不保留长期 open BUY orders，因此 FAK 未成交资金会立即释放。
- 某个 market 因流动性不足买不满预算时，剩余资金分配给其他仍满足条件且未达到上限的 eligible markets。
- 如果没有其他 eligible markets，资金保持可用状态，等待新的 market 或价格机会。
- 每次新 market、价格更新、成交更新、FAK 资金释放或 open order 状态变化后，重新计算资金分配。

## 9. 风控

系统必须提供以下配置：
- `portfolio_budget_usdc`
- `max_order_usdc`
- `max_market_usdc`
- `max_total_usdc`
- `allocation_mode = equal_weight`
- `rebalance_enabled = true`
- `max_open_orders`
- `entry_no_price_max = 0.60`
- `exit_no_price = 0.70`
- `min_liquidity_usdc`
- `max_spread`
- `market_sync_interval_seconds`
- `order_retry_limit`

风控要求：
- 对单个 token / project / event 设置集中度限制。
- 已成交仓位、pending BUY orders 和 open SELL orders 合并计算风险敞口。
- 每个 market 的实际敞口应尽量接近组合平均权重。
- 单个 market 不得因为先发现、流动性更好或多次触发而占用过高资金比例。
- 非 Crypto 分类 markets 不得进入候选池或触发下单。
- 对 resolved、paused、closed、orderbook disabled 的 markets 停止下单。
- 对解析规则不清晰、存在争议或 resolution 条件异常的 markets 停止自动下单。
- 订单失败不得无限重试，需要受 `order_retry_limit` 限制。

## 11. 数据库

数据库使用 PostgreSQL。数据库主要用于复盘、调试和修 bug，不作为交易动作是否已经发生的唯一真相来源；订单、成交和持仓状态必须以 Polymarket API、WebSocket 和链上结果校准。

写入要求：
- 交易主流程不因数据库短暂写入失败而阻塞。
- 关键交易动作先写入可靠 outbox 或等价本地可靠队列。
- 后台 persistence worker 异步落库。
- 落库失败必须可重试、可追踪，避免订单已提交但数据库无记录。

核心表：
- `markets`：保存 event / market 基础信息、slug、conditionId、token_id、筛选命中原因。
- `orderbook_snapshots`：保存 best bid、best ask、spread、可成交流动性、快照时间。
- `portfolio_allocations`：保存每轮资金分配、目标 market budget、剩余可买额度、再分配原因。
- `orders`：保存 FAK BUY orders 与 GTC SELL limit orders 的 order_id、状态、价格、数量、类型。
- `fills`：保存 partial fill / full fill 成交记录。
- `positions`：保存 outcome token 持仓快照。
- `audit_events`：保存完整链路事件、raw_response、error、retry、trace_id。

## 12. 模块

- Market Streamer：实时获取新增 events / markets，并触发筛选。
- Market Classifier：先校验 Crypto 分类，再识别 FDV / 500M target markets，排除误匹配。
- Orderbook Watcher：订阅 `NO token_id` 的 orderbook、best bid、best ask、spread，并用 REST 快照校准。
- Portfolio Allocator：计算 equal-weight 资金分配、单 market 剩余可买额度和未成交资金再分配。
- Strategy Engine：判断入场、FAK 成交/未成交、出场、跳过原因和改价行为。
- Risk Manager：校验单笔、单 market、总投资、组合权重、持仓与 open orders 风险。
- Order Executor：创建、签名、提交、取消、替换 CLOB orders。
- Position Manager：同步 outcome token 持仓、fills 和 open SELL orders。
- Audit Logger：记录完整交易链路。
- Persistence Worker：异步写 PostgreSQL。
- Admin API / CLI：查询用户信息、钱包、余额、持仓、open orders，并支持按 market 批量 cancel + replace。

## 13. 管理功能

系统需要支持：
- 获取 Polymarket 用户信息。
- 获取钱包地址与可用余额。
- 获取 USDC.e 余额。
- 获取 `NO outcome token` / `YES outcome token` 持仓。
- 获取当前账户 open orders。
- 获取历史 orders、fills 和交易状态。
- 检查 CLOB 交易所需 allowance / approval 状态。
- 查询当前命中的 Crypto / FDV / 500M target markets 和 eligible markets。
- 查询每个 market 的资金分配、已用预算、剩余预算和当前持仓。
- 对同一 market / `NO token_id` 下的 open SELL orders 执行批量取消和重新挂单。

## 14. 非目标范围

本系统不包含：
- dry-run / paper trading 模式。
- 非 500M 阈值 markets 的自动交易。
- 买入侧长期 resting BUY limit orders。
- 基于外部 token 上线时间、symbol 或第三方项目资料的新币识别。
- 对 resolved、closed、paused 或 orderbook disabled markets 的继续下单。
