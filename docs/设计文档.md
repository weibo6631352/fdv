# Polymarket FDV 自动交易系统设计文档

本文档基于 [需求文档](./需求文档.md) 编写，覆盖架构设计、模块设计、流程设计和目录设计。

本版本额外加入高性能、多线程 / 异步并发、交易链路优先级和开发规范要求。

官方文档核对点：
- [Polymarket API Introduction](https://docs.polymarket.com/api-reference/introduction)：Gamma API 用于 market/event 发现，Data API 用于用户持仓与交易数据，CLOB API 用于订单簿、价格、下单与撤单。
- [Gamma Markets API](https://docs.polymarket.com/developers/gamma-markets-api/overview)：Gamma 是只读 market 元数据服务，适合获取分类、事件、市场、slug、token 等信息。
- [Fetching Markets](https://docs.polymarket.com/developers/gamma-markets-api/fetch-markets-guide)：主动发现可用 `events?active=true&closed=false` 分页拉取，也可按 tag 或 slug 查询。
- [WebSocket Overview](https://docs.polymarket.com/market-data/websocket/overview)：Market Channel 按 asset id 订阅，User Channel 按 condition id 订阅；`best_bid_ask`、`new_market`、`market_resolved` 需要 `custom_feature_enabled: true`。
- [Create Order](https://docs.polymarket.com/trading/orders/create)：FAK 会立即成交可用部分并取消剩余；GTC 会留在 order book；FAK/FOK 不能与 post-only 组合；market BUY 的 `amount` 表示花费金额，market SELL 的 `amount` 表示卖出 shares。

## 1. 架构设计

### 1.1 设计目标

系统目标是构建一个生产可运行的自动交易服务，持续发现 Polymarket Crypto 分类下符合 FDV 与 500M 条件的 target markets，并在 `NO best ask <= 0.60`、组合资金分配与风控全部通过时买入 `NO outcome token`。

关键约束：
- 买入侧只提交 `FAK BUY`，不允许保留长期 resting BUY order。
- 买入价格上限固定为 `0.60`，作为最差可接受成交价。
- 买入成交后，仅对实际成交数量挂 `GTC SELL at 0.70`。
- 组合资金按 eligible markets 尽量等权分配，FAK 未成交资金立即释放并重新分配。
- 数据库用于审计、复盘和调试，不作为交易状态唯一真相来源。
- 本地状态必须通过 WebSocket 实时事件和 REST 快照定期校准。
- 交易相关链路必须拥有最高运行优先级，核心路径包括 orderbook 更新、入场判断、风控检查、订单签名、订单提交、成交处理和卖单补挂。
- 非交易任务不得阻塞交易链路，包括 Admin API 查询、数据库写入、日志落盘、市场全量扫描、历史回放、指标汇总和 reconcile 的非关键部分。
- 需要充分利用 `asyncio`、多线程执行器和必要的多进程隔离来提升吞吐，所有阻塞 I/O 与 CPU 密集任务必须离开交易主事件循环。
- 交易核心路径不得等待低优先级锁；如必须加锁，应按 market / token 分片，并设置极短超时和明确的降级策略。

### 1.2 推荐技术栈

采用以下后端技术栈：
- 语言：Python 3.12+
- 并发模型：`asyncio`
- 事件循环：生产环境优先启用 `uvloop`，不可用时回退到标准事件循环
- 多线程：使用受控 `ThreadPoolExecutor` 隔离同步 SDK 调用、订单签名、阻塞型文件 I/O 和轻量 CPU 工作
- 多进程：对 CPU 密集型批量分类、历史回放、报表生成等非交易任务使用 `ProcessPoolExecutor` 或独立进程隔离
- Web 框架：FastAPI，仅承载 Admin API 与健康检查
- 数据库：PostgreSQL
- schema 变更策略：当前开发阶段直接调整模型与初始化逻辑，不维护历史 schema 兼容层
- ORM/SQL：SQLAlchemy 2.x 或 SQLModel
- 任务调度：进程内 async worker，后续可替换为 Redis Queue / Celery
- 配置：环境变量 + typed settings
- 运行方式：单体服务优先，模块边界按未来拆分为多进程服务设计

选择理由：
- 交易系统首先需要清晰的状态机、WebSocket 重连、REST 校准和异步 I/O，Python + asyncio 足够直接。
- 交易入口是 I/O 密集型，`asyncio` 负责 WebSocket 和 REST 并发；同步阻塞与 CPU 密集任务通过线程池 / 进程池隔离，避免拖慢交易事件循环。
- 初期用单体部署可以减少跨服务一致性问题，但目录与模块边界保留事件驱动设计，便于后续拆分。
- 交易核心应尽量少依赖 Web 框架，避免把策略逻辑写进 HTTP handler。

### 1.3 总体架构

系统采用事件驱动单体架构，内部通过事件总线串联 market 发现、订单簿更新、策略判断、风控、执行、持仓同步和持久化。

```text
                                                               v
+----------------+     +------------------+       +-----------+-----------+
| CLOB Market WS | --> | Orderbook Watcher| ----> | Strategy Engine      |

                                                               v

                    +-------------------------+   +-----------------------+
```

### 1.4 分层设计

系统按以下层次组织：

| 层级 | 职责 | 典型模块 |
| --- | --- | --- |
| Interfaces | 对外入口，处理 CLI、Admin API、进程启动与信号 | `api`、`cli`、`workers` |
| Application | 编排用例流程，不直接拼接 API payload | `strategy_service`、`reconcile_service`、`admin_service` |
| Domain | 交易规则、筛选规则、风控、资金分配、状态机 | `classifier`、`allocator`、`risk`、`state_machine` |
| Infrastructure | 外部系统适配、数据库、WebSocket、可靠队列 | `polymarket`、`db`、`outbox`、`ws` |
| Observability | 日志、审计、指标、告警 | `audit`、`metrics`、`logging` |

设计原则：
- Domain 层不依赖 Polymarket SDK 的具体对象，使用系统内部 DTO。
- Order Executor 是唯一能提交、取消、替换订单的模块。
- Risk Manager 是下单前的强制门禁，不允许绕过。
- Persistence Worker 异步落库，数据库短暂失败不得阻塞交易主流程。
- Reconciler 以 Polymarket API / WebSocket / 链上结果为状态校准来源。
- 交易链路使用高优先级事件队列和专用执行器，非交易链路只能通过快照读取状态，不得持有会阻塞交易写入的全局锁。

### 1.5 运行时组件

建议启动一个主进程，进程内运行多个 async tasks：

| 组件 | 启动方式 | 核心职责 |
| --- | --- | --- |
| Market Discovery Worker | 常驻任务 | 分页拉取 active events，处理 Market WS `new_market`，触发分类 |
| Market WS Worker | 常驻任务 | 订阅 target market 的 `NO token_id` orderbook 与 best bid/ask |
| User WS Worker | 常驻任务 | 订阅 condition ids，接收订单和成交生命周期事件 |
| Strategy Worker | 事件驱动 | 对价格、资金、持仓、订单变化进行入场判断 |
| Reconcile Worker | 定时任务 | 定期拉取 markets、orderbooks、orders、fills、positions 校准状态 |
| Persistence Worker | 常驻任务 | 从 outbox 消费审计事件和快照，异步写 PostgreSQL |
| Admin API | HTTP 服务 | 查询状态、余额、持仓、open orders，触发人工 cancel/replace |

运行优先级：
- P0：Orderbook Watcher、Strategy Worker、Risk Manager、Order Executor、User WS 中的成交 / 订单状态更新。
- P1：Position Manager、关键 reconcile 修复动作，例如取消异常 open BUY、补挂缺失 SELL。
- P2：Market Discovery、全量 reconcile、余额 / allowance 周期检查。
- P3：Persistence Worker、指标聚合、Admin API 普通查询、报表和历史数据处理。

P0 任务必须使用独立高优先级队列和专用执行器。P2 / P3 任务只能消费状态快照或提交异步请求，不允许反向阻塞 P0。

### 1.6 状态真相来源

状态优先级：
1. Polymarket CLOB / Data API / User WS 的订单、成交、持仓状态。
2. 链上确认状态，用于确认交易最终状态。
3. 本地内存状态，用于策略实时判断。
4. PostgreSQL，用于审计、复盘、调试和恢复时的参考。

恢复策略：
- 启动时先加载配置，再从 PostgreSQL 恢复候选 market 和最近状态。
- 随后调用 Gamma / CLOB / Data API 获取权威快照，覆盖本地过期状态。
- 恢复完成前禁止自动下单。
- 恢复后重新计算 eligible markets、组合预算和 open SELL orders。

### 1.7 高性能与交易优先级设计

目标：
- 在价格触发后尽快完成 `EntryPriceTouched -> RiskCheckPassed -> FAK BUY submitted`。
- 在任何 Admin 查询、数据库抖动、日志阻塞、市场扫描或 reconcile 重任务存在时，交易链路仍保持最高优先级。
- 在高频 orderbook 更新下保持内存状态一致，不因粗粒度锁或跨模块同步等待导致延迟尖刺。

执行模型：
- 主交易事件循环只运行非阻塞 I/O 与轻量状态机逻辑，不直接执行同步 REST SDK、数据库写入、磁盘刷盘、历史扫描或长耗时计算。
- `TradingEventQueue` 使用最高优先级，承载 orderbook price touch、订单状态、成交状态、cancel 异常修复等交易事件。
- `MaintenanceEventQueue` 承载 market discovery、周期 reconcile、余额检查和指标聚合。
- `PersistenceEventQueue` 承载数据库写入、审计 raw JSON 保存、报表快照等持久化工作。
- 订单签名、同步 SDK 适配、阻塞 HTTP fallback 等必须进入专用 `trading_thread_pool`，线程池大小固定且与低优先级线程池隔离。
- 批量分类、历史复盘和报表生成若 CPU 占用明显，应进入 `maintenance_process_pool` 或独立进程，不能占用交易线程池。

锁与状态访问规则：
- 禁止在交易路径上使用全局大锁保护全部 registry / portfolio / position 状态。
- Market Registry、Orderbook Cache、Position State 按 `condition_id` 或 `token_id` 分片，优先使用单 market actor 或 copy-on-write 快照。
- P0 交易写入采用短临界区，只更新必要内存字段，并立即释放锁。
- Admin API、Persistence Worker、指标聚合只读取不可变快照或复制后的视图，不直接长时间持有交易状态锁。
- 如果交易链路获取某个非关键锁超时，应跳过非关键读写并记录告警；不能排队等待低优先级任务释放锁。
- Reconciler 发现必须修复的交易风险时，生成 P1 / P0 修复事件交给交易执行器处理，不在 reconcile 任务内部直接长时间持锁执行订单操作。

背压与降级：
- 各队列必须有容量上限和指标，严禁无限增长导致内存压力拖慢交易。
- P0 队列积压时，优先丢弃或合并低价值的 P2 / P3 快照事件，不能丢弃订单、成交、cancel、risk failure 等关键审计事件。
- 数据库变慢时，Persistence Worker 进入重试和限速，交易主流程继续使用内存状态和 Polymarket 权威快照。
- 日志系统必须异步化；交易路径只能提交结构化日志事件，不同步等待日志落盘。
- Admin API 查询需要分页、限流和快照读取，大查询不得扫描交易热路径结构。

延迟监控：
- 记录 `orderbook_event_received_at`、`entry_signal_at`、`risk_passed_at`、`order_signed_at`、`order_submitted_at`、`order_ack_at`。
- 监控 `entry_signal_to_submit_ms`、`ws_event_lag_ms`、`trading_queue_depth`、`trading_lock_wait_ms`、`executor_queue_wait_ms`。
- 当交易队列等待、锁等待或订单提交延迟超过阈值时，触发告警并暂停低优先级任务。

## 2. 模块设计

### 2.1 Market Streamer

职责：
- 从 Gamma API 拉取 `active=true&closed=false` 的 events 和关联 markets。
- 订阅 Market WS 的 `new_market` 事件作为新增 market 的低延迟入口。
- 将 event / market 原始数据转换为内部 `RawMarketEvent`。
- 对新增、更新、分页扫描结果做去重。

输入：
- Gamma `events` / `markets` 响应
- Market WS `new_market`

输出：
- `MarketDiscovered`
- `MarketUpdated`

关键规则：
- 去重优先使用 `condition_id`，其次使用 `market_slug`。
- 对分页拉取和 WS 新增事件都要走同一套分类流程。
- 发现时间、来源和原始响应摘要必须进入审计日志。

### 2.2 Market Classifier

职责：
- 对 market 做 Crypto 分类校验。
- 识别 FDV event 和 500M threshold market。
- 排除 150M、300M、800M、1B 等非目标阈值。
- 解析 `YES token_id`、`NO token_id`、`tick_size`、`min_order_size`、`neg_risk`。

输入：
- `RawMarketEvent`

输出：
- `TargetMarketAccepted`
- `TargetMarketRejected`

关键规则：
- Crypto 分类是硬前置条件，Pre-Market 只能作为附加标签。
- FDV 命中必须来自 event title 或明确等价字段。
- 500M 命中必须来自 market question、market name 或 slug。
- 不使用宽泛 `valuation` 作为独立命中条件。
- 对分类不清晰、文本有争议、resolution 异常的 market 输出拒绝原因。

### 2.3 Market Registry

职责：
- 保存本地 target market 状态。
- 维护 `condition_id -> market`、`no_token_id -> market`、`slug -> market` 索引。
- 维护 market 生命周期状态：candidate、eligible、paused、closed、resolved、rejected。

核心字段：
- `event_id`、`event_title`、`event_slug`
- `market_slug`、`condition_id`
- `yes_token_id`、`no_token_id`
- `tick_size`、`min_order_size`、`neg_risk`
- `category`、`tags`、`matched_keywords`
- `trading_status`、`reject_reason`

### 2.4 Orderbook Watcher

职责：
- 按 `NO token_id` 订阅 CLOB Market Channel。
- 接收 `book`、`price_change`、`best_bid_ask`、`tick_size_change`、`last_trade_price`、`market_resolved`。
- 维护本地 orderbook cache 和 best bid/ask。
- 计算 spread、可成交深度、`NO best ask <= 0.60` 信号。
- 断线后重连，并通过 REST 快照校准。

输入：
- Market WS 消息
- CLOB REST orderbook 快照

输出：
- `OrderbookSnapshotUpdated`
- `EntryPriceTouched`
- `MarketResolvedOrDisabled`

关键规则：
- 订阅 Market Channel 时开启 `custom_feature_enabled: true`，以接收 `best_bid_ask`、`new_market`、`market_resolved`。
- 只对 `NO token_id` 的 ask 侧计算买入可成交深度。
- `tick_size_change` 必须更新 Market Registry 中对应 market 的 tick size。
- 发现序列缺失或重连后，必须用 REST 快照覆盖本地 orderbook。
- orderbook 热路径只更新内存快照并投递 P0 交易事件，严禁同步写数据库、同步写日志或等待 Admin / Persistence / Reconcile 持有的低优先级锁。
- 高频 price change 可以按 market 合并非关键快照，但触发 `NO best ask <= 0.60` 的首次穿越事件必须立即进入 P0 队列。

### 2.5 Portfolio Allocator

职责：
- 对当前 eligible markets 计算等权目标预算。
- 计算每个 market 剩余可买额度。
- 将 FAK no fill / partial fill 释放的资金重新分配给仍可买入 markets。

输入：
- `portfolio_budget_usdc`
- `eligible_markets`
- 每个 market 已成交 notional
- pending BUY、open SELL、持仓快照
- orderbook 可成交深度

输出：
- `AllocationPlan`
- `MarketBuyBudgetChanged`

算法：
1. 过滤出 eligible markets：分类通过、可交易、`NO best ask <= 0.60`、流动性与 spread 通过、风控未触顶。
2. 计算基础目标预算：`portfolio_budget_usdc / eligible_market_count`。
3. 对每个 market 取 `min(target_market_budget, max_market_usdc - current_exposure)`。
4. 再取 `min(remaining_market_budget, max_order_usdc, available_usdc, executable_depth_usdc)`。
5. 若某 market 因深度不足、min order size 或风控不能买满，则释放差额。
6. 对剩余 eligible markets 重复分配，直到没有可分配资金或没有可买 market。

说明：
- `current_exposure` 包含已成交持仓成本、pending BUY、open SELL 对应的底层持仓成本。
- 因买入侧只用 FAK，正常情况下 pending BUY 应接近 0；若出现 resting BUY 异常，风险模块必须触发取消。

### 2.6 Risk Manager

职责：
- 在任何下单前执行强制风控检查。
- 对 market、event、token、project 和组合级别进行集中度控制。
- 对异常 market 状态、异常订单状态和失败重试进行拦截。

输入：
- `OrderIntent`
- `AllocationPlan`
- market 状态、orderbook 状态、position 状态、open orders
- runtime config

输出：
- `RiskCheckPassed`
- `RiskCheckFailed`

检查项：
- 分类必须是 Crypto + FDV + 500M。
- market 必须 active、open、CLOB enabled、未 resolved / cancelled / archived。
- `NO best ask <= entry_no_price_max`。
- price 必须符合 `tick_size`。
- notional 必须满足 `min_order_size`。
- 单笔不超过 `max_order_usdc`。
- 单 market 不超过 `max_market_usdc`。
- 策略总投入不超过 `max_total_usdc`。
- open orders 数量不超过 `max_open_orders`。
- spread 不超过 `max_spread`，深度不低于 `min_liquidity_usdc`。
- order retry 次数不超过 `order_retry_limit`。
- 买入侧不得存在长期 open BUY order。
- 地理限制、allowance 和余额检查必须通过。
- 下单前风控必须只读取本地热状态和已同步快照，不得在 P0 路径中临时发起慢 REST 查询或数据库查询。

### 2.7 Strategy Engine

职责：
- 根据 market、orderbook、allocation、position、risk 状态生成交易意图。
- 处理 FAK 买入结果并触发 GTC 卖出。
- 处理跳过原因，避免无意义重试。

输入事件：
- `TargetMarketAccepted`
- `OrderbookSnapshotUpdated`
- `EntryPriceTouched`
- `AllocationPlanUpdated`
- `OrderMatched`
- `OrderPartiallyFilled`
- `OrderNoFill`
- `OrderRejected`
- `PositionUpdated`

输出：
- `BuyOrderIntent`
- `SellOrderIntent`
- `CancelOrderIntent`
- `ReplaceOrderIntent`
- `StrategySkipped`

关键规则：
- 入场只由 `NO best ask <= 0.60` 触发。
- FAK BUY 内部记录 `target_notional_usdc` 和预估 shares；Polymarket SDK 适配层按 market order 语义传入 BUY `amount=target_notional_usdc`、`price=0.60`。
- FAK full fill 或 partial fill 后，按实际成交 shares 创建 `GTC SELL at 0.70`。
- FAK no fill 后释放全部预算并触发再分配。
- rejected / failed 按原因记录，不无限重试。
- 如果买入订单返回 `live` 或本地发现 open BUY，立即发起 cancel 并记录异常。
- Strategy Worker 只消费高优先级交易事件和必要状态快照，不等待 Admin 查询、报表、全量 reconcile 或数据库落库。
- 同一 market 的非关键价格刷新可以合并处理，但订单状态、成交状态、异常 open BUY 和首次入场信号不得合并丢失。

### 2.8 Order Executor

职责：
- 唯一负责订单创建、签名、提交、取消和替换。
- 适配 Polymarket CLOB SDK 或 REST API。
- 维护幂等键，避免相同信号重复下单。

输入：
- `BuyOrderIntent`
- `SellOrderIntent`
- `CancelOrderIntent`
- `ReplaceOrderIntent`

输出：
- `OrderCreated`
- `OrderSigned`
- `OrderSubmitted`
- `OrderRejected`
- `OrderCancelRequested`
- `OrderCancelled`
- `ReplaceOrderSubmitted`

关键实现：
- 下单前写入可靠 outbox 事件，包含 `trace_id` 和 intent 摘要。
- FAK BUY：`order_type=FAK`，`post_only=false`，price 为 `0.60`，BUY amount 为 USDC.e 花费金额。
- GTC SELL：`order_type=GTC`，price 为 `0.70`，size 为已成交 NO shares。
- cancel + replace：先确认 cancel 成功或订单已终态，再提交新 SELL。
- 批量下单只用于明确安全的 SELL 场景；入场买入优先单笔执行，方便审计和预算释放。
- Order Executor 使用专用 P0 队列和专用 `trading_thread_pool`，不得与报表、Admin API、批量 market discovery 共享线程池。
- 订单签名、HTTP 提交和 cancel 请求必须设置明确超时，并记录排队耗时、签名耗时、提交耗时和 ACK 耗时。
- 关键 outbox 写入采用本地 append-only 快路径和短超时；数据库慢或日志慢时，不得阻塞订单提交线程。
- 幂等检查优先使用内存中的短临界区结构，不能为了幂等性在 P0 路径中执行慢数据库查询。

### 2.9 Position Manager

职责：
- 同步账户余额、USDC.e、outcome token 持仓、open orders、fills。
- 维护每个 market 的已成交仓位与 open SELL orders。
- 根据 User WS 事件更新订单和成交生命周期。

输入：
- User WS `order` / `trade`
- Data API positions / trades
- CLOB open orders / fills

输出：
- `BalanceUpdated`
- `PositionUpdated`
- `OrderStateUpdated`
- `FillRecorded`

关键规则：
- User Channel 按 condition id 订阅，而不是按 token id。
- trade 状态按 `MATCHED -> MINED -> CONFIRMED` 及 `RETRYING` / `FAILED` 处理。
- 成交状态未确认时可以更新风险占用，但最终收益统计以确认后的状态为准。
- open SELL orders 和实际持仓不一致时，进入 reconcile 流程。

### 2.10 Reconciler

职责：
- 定期校准本地状态，修复 WS 丢消息、重连和数据库落后导致的不一致。

校准对象：
- market 是否仍 active / open / CLOB enabled。
- orderbook best bid/ask 与深度。
- open BUY / SELL orders。
- fills 和 trade confirmation。
- outcome token positions。
- USDC.e 可用余额与 allowance。

输出：
- `ReconcileStarted`
- `ReconcileDiffDetected`
- `ReconcileApplied`
- `TradingPausedForMarket`

关键规则：
- 发现 open BUY order 必须取消。
- 发现 market closed/resolved/disabled，停止新买入，并根据配置处理 open SELL。
- 发现持仓大于 open SELL 数量，可补挂 SELL；发现 open SELL 数量大于持仓，需要取消多余 SELL。
- Reconciler 的批量扫描属于 P2；只有异常 open BUY、缺失 SELL 补挂、market 不可交易暂停等修复动作可以升级为 P1 / P0 事件。
- Reconciler 不得长时间持有 Market Registry、Position State 或 Orderbook Cache 的写锁。

### 2.11 Audit Logger

职责：
- 记录完整交易链路，保证复盘时能从 market discovery 追溯到每一次订单动作。
- 为每条链路生成并传播 `trace_id`。

事件类型：
- 沿用需求文档中的 `market_discovered`、`market_filtered_in`、`entry_signal_triggered`、`risk_check_passed`、`order_submitted`、`order_matched`、`exit_order_submitted`、`trade_confirmed` 等事件。

关键规则：
- 交易动作先写可靠 outbox，再异步落库。
- raw response 做长度限制和敏感信息脱敏。
- 对错误、跳过、重试同样记录完整原因。
- Audit Logger 不得在交易热路径同步写 PostgreSQL 或阻塞文件日志；只允许提交轻量结构化事件到可靠 outbox。
- 大体积 raw response、调试快照和指标事件属于低优先级持久化，必须与订单提交事件分队列处理。

### 2.12 Persistence Worker

职责：
- 消费 outbox，将审计事件、市场快照、订单、成交、持仓和资金分配写入 PostgreSQL。
- 对数据库失败做可重试、可追踪处理。

关键规则：
- 数据库失败不阻塞交易主流程。
- 写入使用幂等键，例如 `event_type + trace_id + order_id + status`。
- 关键表建议保留 raw JSON 字段，以便适配 Polymarket 响应变化。
- Persistence Worker 属于 P3 任务，数据库连接池必须与交易 REST / WS 连接资源隔离。
- 落库积压时优先保留交易审计事件，低优先级状态快照可以合并、降采样或延后写入。

### 2.13 Admin API / CLI

职责：
- 提供只读查询和受控人工操作。

查询能力：
- 当前 target markets / eligible markets。
- 每个 market 的 best bid/ask、spread、深度、资金分配、持仓、open orders。
- 账户余额、USDC.e、allowance、positions、orders、fills。
- 策略运行状态、WS 连接状态、最近 reconcile 时间。

操作能力：
- 按 market / `NO token_id` 查询 open SELL orders。
- 批量取消 open SELL orders。
- 执行 cancel + replace，将 open SELL 改挂新价格。
- 暂停 / 恢复某个 market 的自动买入。
- 全局暂停新买入。

限制：
- 不提供 dry-run / paper trading 模式。
- 不允许通过 Admin API 绕过 Risk Manager 直接下 FAK BUY。
- Admin API 查询只能读取快照或仓储层数据，禁止持有交易热状态写锁。
- Admin API 大查询必须分页和限流，不能与 Order Executor 共享线程池。

## 3. 流程设计

### 3.1 系统启动流程

1. 加载配置和密钥，检查必填项。
2. 初始化日志、指标、outbox、数据库连接和 Polymarket clients。
3. 初始化 P0 `TradingEventQueue`、专用 `trading_thread_pool`、P2 / P3 维护队列和线程池 / 进程池。
4. 执行地理限制、余额、allowance、API credential 检查。
5. 从 PostgreSQL 加载最近的 target markets、orders、positions 作为恢复参考。
6. 调用 Gamma / CLOB / Data API 拉取权威快照。
7. 用快照覆盖本地状态，标记不一致项并写审计日志。
8. 启动 Market Discovery、Market WS、User WS、Reconciler、Persistence Worker。
9. 完成首次 reconcile 后，允许策略进入自动下单状态。

### 3.2 Market 发现与筛选流程

1. Market Streamer 从 Gamma API 分页拉取 active events，或从 Market WS 收到 `new_market`。
2. 对 event / market 生成 `trace_id`，写入 `market_discovered`。
3. Market Classifier 先检查 Crypto 分类。
4. 检查 event title 是否包含 FDV / fully diluted valuation。
5. 检查 market question、name、slug 是否包含 500M 目标阈值。
6. 排除其他阈值和信息不清晰 market。
7. 解析 `condition_id`、`NO token_id`、`YES token_id`、`tick_size`、`min_order_size`、`neg_risk`。
8. 通过则写入 Market Registry，并订阅 Market WS 的 `NO token_id` 和 User WS 的 `condition_id`。
9. 不通过则写入 `market_filtered_out`，保留拒绝原因和命中字段。

### 3.3 Orderbook 监听与入场信号流程

1. Orderbook Watcher 订阅 target market 的 `NO token_id`。
2. 首次收到 `book` 后更新本地 orderbook。
3. 收到 `best_bid_ask` 或 `price_change` 后更新 best ask、best bid、spread 和深度。
4. 若 market resolved、closed、orderbook disabled 或状态异常，标记 market paused 并停止买入。
5. 当 `NO best ask <= 0.60`，生成 `EntryPriceTouched`。
6. Strategy Engine 请求 Portfolio Allocator 计算当前可买预算。
7. Risk Manager 执行风控检查。
8. 风控通过后生成 `BuyOrderIntent`。
9. 风控失败则写 `risk_check_failed` 和 `skipped`。

### 3.4 FAK 买入流程

1. Strategy Engine 根据 allocation 得到 `target_notional_usdc`。
2. 根据 orderbook ask 侧深度估算可成交 shares 和实际 notional。
3. 检查 `notional >= min_order_size`，否则跳过并释放预算。
4. Order Executor 写入 outbox：`order_created`。
5. Order Executor 创建并签名 FAK BUY：`token=NO token_id`，`price=0.60`，`amount=target_notional_usdc`，`post_only=false`。
6. 签名与提交走专用 P0 执行器，不得等待数据库、Admin 查询、指标聚合或低优先级锁。
7. Order Executor 提交订单，写入 `order_submitted`。
8. 若返回 full fill 或 User WS 收到对应 matched，记录成交并进入卖出流程。
9. 若 partial fill，仅对已成交 shares 进入卖出流程，未成交资金释放并触发再分配。
10. 若 no fill，释放全部买入预算，记录 `order_no_fill`。
11. 若 rejected / failed，记录原因，按 `order_retry_limit` 控制重试。
12. 若订单异常进入 `live` 或本地发现 open BUY，立即 cancel 并写 `resting_buy_detected`。

### 3.5 GTC 卖出流程

1. Position Manager 确认 FAK 买入实际成交 shares。
2. Strategy Engine 生成 `SellOrderIntent`：`SELL NO token_id at 0.70`。
3. Risk Manager 检查持仓、allowance、market 状态和 open orders 数量。
4. Order Executor 创建并签名 GTC SELL，size 等于实际成交 NO shares。
5. 提交成功后写 `exit_order_submitted`。
6. User WS 收到 partial fill 时，更新剩余 open SELL。
7. User WS 收到 full fill 或 confirmed 时，更新 position 和 realized PnL。
8. market 关闭、风控要求或人工操作触发时，执行 cancel 或 cancel + replace。

### 3.6 资金再分配流程

1. 任一事件触发重算：新 target market、价格更新、成交更新、FAK no fill、FAK partial fill、订单取消、持仓校准。
2. Portfolio Allocator 重新计算 eligible markets。
3. 计算每个 market 当前 exposure。
4. 对低于等权目标且仍满足价格与风控条件的 markets 分配预算。
5. 对已达到单 market 上限或流动性不足的 markets 不再分配。
6. 若仍有未分配资金且存在其他 eligible market，继续分配。
7. 若没有 eligible market，资金保持可用，等待下次触发。

### 3.7 Reconcile 流程

1. 定时启动 reconcile，也可由 WS 重连后立即触发。
2. 拉取 active target markets 的 Gamma 快照，校验 active、closed、archived、enableOrderBook。
3. 拉取 CLOB orderbook 快照，覆盖本地 best bid/ask 和深度。
4. 拉取 open orders、fills、positions、USDC.e balance 和 allowance。
5. 对比本地状态与权威快照。
6. 对差异执行修复：
   - open BUY 存在：立即 cancel。
   - 持仓 shares 大于 open SELL shares：按差额补挂 GTC SELL。
   - open SELL shares 大于持仓 shares：取消多余 SELL。
   - market 不可交易：暂停新买入。
7. 写入 reconcile 审计事件和 PostgreSQL 快照。

### 3.8 Admin cancel + replace 流程

1. Admin API 接收 market slug / condition id / NO token id 和新卖出价格。
2. 查询该 market 下本账户所有 open SELL orders。
3. 校验目标价格符合 tick size，market 可操作，持仓数量足够。
4. 逐个取消 open SELL orders。
5. 确认取消成功或订单已终态。
6. 按剩余可卖 shares 提交新的 GTC SELL。
7. 记录 `order_cancel_requested`、`order_cancelled`、`replace_order_submitted`。

### 3.9 异常处理流程

| 异常 | 处理方式 |
| --- | --- |
| Market WS 断线 | 指数退避重连，重连后 REST 快照校准 |
| User WS 断线 | 暂停新买入，重连并完成订单/持仓 reconcile 后恢复 |
| Gamma API 拉取失败 | 保留已有 markets，延迟重试，不新增未知 market |
| CLOB 下单失败 | 记录错误，按 retry limit 控制重试 |
| DB 写入失败 | outbox 保留，Persistence Worker 重试 |
| 余额或 allowance 不足 | 暂停新买入，Admin API 暴露告警 |
| 买入订单进入 live | 立即 cancel，暂停该 market，写异常审计 |
| market resolved/closed | 停止买入，取消或保留 SELL 按风控配置处理 |
| 低优先级任务阻塞 | 暂停或限速 P2 / P3 任务，P0 交易队列继续运行 |
| 交易锁等待超时 | 跳过非关键状态写入并告警；关键订单状态进入 P0 修复流程 |

### 3.10 高优先级交易事件处理流程

1. Market WS 收到 best ask 更新，Orderbook Watcher 更新对应 market 的内存快照。
2. 若首次满足 `NO best ask <= 0.60`，立即投递 `EntryPriceTouched` 到 P0 `TradingEventQueue`。
3. Strategy Worker 从 P0 队列读取事件，基于本地快照请求 Portfolio Allocator 计算可买金额。
4. Risk Manager 在内存快照上完成风控检查，不发起慢 REST 查询或数据库查询。
5. Order Executor 在专用交易执行器中完成幂等检查、签名和 FAK BUY 提交。
6. User WS 收到 matched / partial fill / no fill 后，订单和持仓状态更新事件进入 P0 队列。
7. 对 full fill / partial fill 的实际成交 shares，立即生成 GTC SELL intent，并通过同一交易执行器提交。
8. 审计事件以轻量结构进入 outbox，数据库写入由 P3 Persistence Worker 异步完成。
9. 若 P0 队列积压或延迟超过阈值，Supervisor 自动限速 Market Discovery、Admin 大查询、报表和低优先级 reconcile。

| `AuditEvent` | trace id、事件类型、原因、raw response 摘要 |
| `OutboxEvent` | 待持久化事件、幂等键、重试次数、最后错误 |

### 4.4 测试重点

专项验收阶段优先覆盖以下测试场景：
- Crypto 分类先于 FDV / 500M 匹配。
- FDV event + 500M market 才能进入 target pool。
- 非 500M 阈值被排除。
- `NO best ask > 0.60` 不触发买入。
- FAK partial fill 只对成交 shares 挂 SELL。
- FAK no fill 会释放预算并重新分配。
- open BUY 异常会触发 cancel。
- 等权分配不会让早发现 market 超过 `max_market_usdc`。
- User WS 断线后恢复必须完成 reconcile 才允许继续买入。
- DB 写入失败不阻塞订单提交，但 outbox 可重试。
- Admin API 大查询、数据库慢写入、日志落盘变慢时，FAK BUY 提交路径仍不被阻塞。
- P0 交易队列优先于 P2 / P3 队列执行，低优先级任务积压不会占用交易线程池。
- 交易热路径遇到低优先级锁等待超时时，会跳过非关键操作并记录告警。
- 高频 orderbook 更新可以合并非关键快照，但首次价格触发事件不能丢失。
- 性能测试覆盖 `entry_signal_to_submit_ms`、`trading_queue_depth` 和 `trading_lock_wait_ms` 阈值。

## 5. 开发规范

### 5.1 编码与文件格式

- 所有源码、配置示例、Markdown 文档和测试文件统一使用 UTF-8 编码，推荐无 BOM。
- 仓库统一使用 LF 换行，避免混用 CRLF 导致脚本、测试或部署环境出现差异。
- Python 代码以 Python 3.12+ 为目标版本，公共函数、核心 DTO、配置对象和领域模型必须补充类型标注。
- 配置、密钥和运行时路径不得硬编码到业务代码；密钥类配置不得进入仓库。
- 业务变量和代码标识建议使用英文，用户可见文案、业务规则说明和注释使用规范中文。

### 5.2 中文注释规范

- 新增模块、公共函数、DTO、worker、路由、外部适配器和关键状态机时，需要补充标准文档注释或等价说明，写清职责、输入输出、关键约束、副作用、异常处理和依赖边界；文档注释应随实现同步更新，过期注释视为缺陷。
- 需要中文注释的位置：核心交易规则、风控原因、并发边界、锁使用原因、外部 API 适配差异、异常降级策略和难以从代码直接看出的业务约束。
- 注释应解释“为什么这样做”和“违反后会发生什么”，避免重复描述代码本身。
- 对交易关键路径中的锁、队列、线程池、超时和降级逻辑，必须写清楚中文注释，方便审计和后续维护。
- 对 Polymarket SDK / REST / WebSocket 的字段语义差异，必须在适配层用中文注释说明，例如 BUY market order 的 `amount` 表示 USDC.e 花费金额，SELL 的 `amount` 表示 shares。
- 禁止在注释中记录私钥、API key、账户敏感信息、完整签名 payload 或未脱敏的 raw response。

### 5.3 并发与性能开发规范

- 交易热路径禁止同步数据库查询、同步日志落盘、阻塞文件 I/O、无限等待锁和无超时网络请求。
- 所有队列必须有容量上限、优先级定义和监控指标；新增 worker 时必须说明所属优先级。
- 新增锁必须说明保护的数据、锁粒度、最大等待时间和超时后的降级策略。
- 新增线程池 / 进程池任务必须明确是否属于 P0、P1、P2 或 P3，P0 任务不得与低优先级任务共享执行器。
- Admin API、报表、历史回放和批量扫描只能读取快照或仓储数据，不得直接阻塞交易状态写入。
- 对交易路径新增外部调用时，必须设置超时、重试上限、幂等键和结构化审计事件。

### 5.4 代码审查与测试规范

- 开发过程中不运行测试；测试清单维护和执行统一安排在专项验收阶段。
- 如果实现过程中发现需求、设计或计划文档存在遗漏、歧义、不合理约束或 bug，需要及时反馈并推动讨论对齐；设计可能存在未考虑到的场景，允许提出更优方案，确认后同步更新文档。
- 当前开发阶段直接修改模型、初始化逻辑和开发环境数据，不引入旧 schema 兼容方案。
- 开发过程中尽量不要轻易带入历史遗留问题、兼容包袱或为了未来假设场景预埋复杂机制；如果某个设计明显是在为不存在的旧版本或历史数据让路，需要先说明真实必要性。
- 为阶段性开发或专项验证临时增加的测试专用接口、调试入口、测试开关或旁路逻辑，在验证通过后应及时删除，不得长期保留在正式源码中增加理解和维护成本。
- 如果确实需要为测试补充扩展点，优先在 `tests` 目录通过 fixture、fake、stub、测试 helper 或测试数据构造完成；除非无法避免，不要在 `src` 中直接新增测试专用接口。若必须新增，需要在说明中写清原因、影响范围和清理计划。
- 涉及下单、撤单、成交、持仓、资金分配、风控和 reconcile 的改动，需要在专项验收阶段补齐或更新对应测试场景。
- 涉及并发、线程池、锁、队列和降级策略的改动，需要在专项验收阶段补齐延迟、超时或优先级相关测试场景。
- 专项验收阶段应显式模拟数据库慢、日志慢、Admin 查询慢、低优先级队列积压和 WS 重连等场景。
- PR / 提交说明必须标注是否影响 P0 交易链路，以及是否新增锁、队列、线程池或外部调用。
- 性能相关指标超过阈值时，应优先定位交易队列积压、锁等待、线程池饱和和外部 API 延迟。
