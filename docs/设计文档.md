# 交易框架设计文档

本文档描述框架结构、模块边界和现有扩展点，不描述某个具体策略的筛选词、阈值和仓位规则。

配套文档：

- 框架需求：[`需求文档.md`](./需求文档.md)
- 管理接口：[`api.md`](./api.md)

## 1. 设计目标

框架要解决三件事：

1. 把 Polymarket 的实时数据、快照数据和交易执行接进来。
2. 把策略决策和基础设施解耦。
3. 把交易、恢复、持久化和管理接口放进统一运行时。

## 2. 总体结构

代码目录按职责拆成以下几层：

| 层 | 目录 | 责任 |
| --- | --- | --- |
| 接口层 | `src/polymarket_trader/api/` | Admin API、健康检查、参数校验、响应序列化 |
| 应用层 | `src/polymarket_trader/app/` | 编排用例，连接策略、运行时状态和基础设施 |
| 领域层 | `src/polymarket_trader/domain/` | 市场、订单、成交、持仓、风控、状态机等通用模型 |
| 基础设施层 | `src/polymarket_trader/infra/` | Polymarket 客户端、数据库、outbox、持久化 |
| 运行时层 | `src/polymarket_trader/runtime/` | registry、event bus、scheduler、supervisor |
| 扩展宿主层 | `src/polymarket_trader/app/strategy_host/` | 业务扩展加载、重放工具、装配入口 |
| 应用端口层 | `src/polymarket_trader/app/ports/` | 面向业务扩展的应用层读取接口适配 |
| 扩展 API | `src/polymarket_trader/extension_api/` | 仓库内部业务扩展 SPI：扩展契约、上下文对象、端口与配置加载 |
| 扩展实现层 | `src/strategies/` | 顶层具体业务扩展实现；当前策略只是一个示例扩展 |
| worker 层 | `src/polymarket_trader/workers/` | 常驻后台任务和实时处理链路 |

## 3. 运行时装配

当前装配入口：

- `src/polymarket_trader/main.py`

`build_runtime()` 负责组装：

- 配置与启动校验
- Polymarket 各类客户端
- 事件总线和本地 outbox
- 数据库 session factory 与持久化仓储
- 市场状态、账户状态和指标注册表
- 交易执行器
- 各类 worker
- 应用服务
- 调度器和 supervisor

运行时通过 `Settings.extension_module` 选择业务扩展包，并由 `app/strategy_host/loader.py` 装配。`extension_config_path` 可指向扩展自己的外部配置文件。`main.py` 先创建 `StrategyPorts`，在 `MarketWsWorker` 创建后再把 live orderbook reader 绑定到 `ports.market`。框架只向扩展暴露市场、盘口、账户、预算等上下文，以及原始 `EntryCandidate` 候选列表；具体的 universe 判断、目标 token、入场价格、退出价格、深度和 spread 阈值都由扩展自己的 `ExtensionHooks.size_entry()` / `decide_entry()` / `decide_exit()` / `decide_follow_up()` 处理。`polymarket_trader.extension_api` 当前定位为仓库内部业务扩展 SPI，不承诺外部产品化 SDK 的长期兼容语义。

## 4. 核心调用链

### 4.1 市场发现链路

```text
Gamma / discovery query
-> MarketDiscoveryWorker
-> MarketService
-> ExtensionHooks.select_market()
-> MarketRegistry
-> MarketWsWorker 订阅管理
```

### 4.2 交易判断链路

```text
Market WS / User WS
-> EventBus
-> StrategyWorker
-> StrategyService
-> ExtensionHooks.size_entry() / decide_entry() / decide_exit() / decide_follow_up()
-> TradingService
-> OrderExecutor
```

### 4.3 恢复链路

```text
定时调度或 Admin API
-> ReconcileWorker
-> ReconcileService
-> ExtensionHooks.decide_recovery()
-> TradingService / Registry / AccountStateStore
```

### 4.4 持久化链路

```text
Domain event / runtime snapshot
-> LocalOutbox
-> PersistenceWorker
-> DatabasePersistenceRepository
-> PostgreSQL
```

## 5. 组件职责

### 5.1 Interface

- `api/app.py`：创建 FastAPI 应用并注册路由。
- `api/routes/*.py`：按资源拆分 handler。
- `AdminService`：管理查询和人工操作的统一入口。

要求：

- route 不直接操作交易客户端。
- route 不直接读写运行时内部可变状态。

### 5.2 Application

- `market_service.py`：市场发现、分类、注册和订阅相关编排。
- `strategy_service.py`：把策略决策桥接成订单意图。
- `trading_service.py`：统一交易动作入口。
- `reconcile_service.py`：恢复和修复动作编排。
- `admin_service.py`：管理查询和受控操作。

要求：

- application 层不保存第二份业务真相。
- application 层不硬编码某个策略的具体阈值语义。

### 5.3 Domain

通用模型放在 `domain/`，例如：

- `market.py`
- `order.py`
- `position.py`
- `orderbook.py`
- `events.py`
- `allocation.py`
- `risk.py`
- `state_machine.py`

要求：

- 领域对象表达通用交易概念，不表达某个具体策略名字。
- 字段命名必须单义，避免对外和对内使用不同名字描述同一件事。

### 5.4 Infrastructure

- `infra/polymarket/`：Gamma、CLOB、Data、WS、执行客户端适配。
- `infra/db/`：SQLAlchemy model、repository、持久化入口。
- `infra/outbox/`：本地 outbox 与事件投递。

要求：

- SDK 细节留在 infra。
- 上层只消费框架内部 DTO、仓储和服务。

### 5.5 Runtime

- `MarketRegistry`：市场索引和订阅目标基础数据。
- `AccountStateStore`：余额、订单、成交、持仓等内存状态。
- `EventBus`：交易、维护、持久化链路的事件队列。
- `Supervisor` / `Scheduler`：任务状态与周期调度。

## 6. Worker 设计

当前 worker：

| 文件 | 责任 |
| --- | --- |
| `market_discovery_worker.py` | 发现 markets 并提交分类处理 |
| `market_ws_worker.py` | 接收盘口和市场状态更新 |
| `user_ws_worker.py` | 接收订单、成交、持仓相关更新 |
| `strategy_worker.py` | 消费交易相关事件并触发策略判断 |
| `reconcile_worker.py` | 周期校准和恢复 |
| `persistence_worker.py` | 异步持久化 |

边界要求：

- worker 负责搬运消息和调度，不负责写策略规则。
- 交易主链路 worker 不能被持久化、日志或管理查询反向阻塞。

## 7. 策略扩展点

框架真正的策略契约在：

- `src/polymarket_trader/extension_api/hooks.py`
- `src/polymarket_trader/extension_api/context.py`
- `src/polymarket_trader/extension_api/decisions.py`
- `src/polymarket_trader/extension_api/ports.py`
- `src/polymarket_trader/extension_api/manifest.py`

业务扩展通过 manifest 暴露 `BusinessExtension`，并提供 `ExtensionHooks` 实现：

- `build_discovery_queries()`
- `select_market()`
- `size_entry()`
- `decide_entry()`
- `decide_exit()`
- `decide_recovery()`
- `decide_follow_up()`
- `should_keep_tracking()`
- `build_filtered_tracking_market()`

补充约束：

- `StrategyDecision` 必须由策略显式给出 `token_id`、`action`、`order_type`、`price`、`size` 等交易形状；框架不再默认把某个 market 的 `NO` outcome 当作唯一目标。
- `RecoveryDecision` 只表达策略希望执行的动作集合与暂停语义，框架负责把这些动作翻译成 submit / cancel / replace 执行。
- runtime 只暴露通用 `allow_new_entries` gate，不再把“是否允许新开仓”命名成固定的 `buy` 语义。

仓库内置一个示例策略实现：

- `src/strategies/current/strategy.py`

策略文件入口：

- discovery：`discovery.py`
- 市场筛选：`universe.py`
- 分配、入场、退出：`trading.py`
- 恢复：`recovery.py`
- 订阅保留规则：`tracking.py`
- 策略参数常量：`config.py`

框架要求：

- 策略输出决策对象，不直接调用交易客户端。
- 策略可影响 discovery、universe、sizing、entry、exit、recovery。
- 订阅创建和移除仍由框架控制。

## 8. 状态真相来源

优先级：

1. Polymarket 实时事件与权威快照。
2. 本地内存状态。
3. PostgreSQL 审计与快照。

设计原则：

- 交易实时判断依赖内存状态。
- 权威修正依赖 WS 和 REST。
- 数据库用于查询、审计、恢复参考，不作为交易唯一真相来源。

## 9. 管理接口设计

Admin API 只承载：

- 健康检查和运行态查询
- 市场、订单、成交、持仓、组合数据查询
- 审计、分配、outbox 查询
- 人工 reconcile
- 人工 order replace

它不承载：

- 策略计算
- 自动下单入口
- 交易客户端直连

路由明细以 `docs/api.md` 为准。

## 10. 配置设计

配置分两类：

### 10.1 框架配置

由 `.env` 和 `Settings` 管理，例如：

- host / ws 地址
- 钱包和交易凭据
- 数据库
- 线程池和队列大小
- 超时、重试和通用风控上限

### 10.2 策略配置

不属于框架公共契约。

现有装配方式：

- 框架通过 `EXTENSION_MODULE` 选择业务扩展包。
- 当前示例扩展位于 `src/strategies/current/`，可通过 `EXTENSION_MODULE=strategies.current` 装配。
- 框架不强制策略参数必须来自 `.env`。
- 运行时支持通过 `EXTENSION_CONFIG_PATH` 和 `polymarket_trader.extension_api.config_loader` 加载扩展侧外部配置。

## 11. 并发与优先级

当前运行时已经把资源分成：

- `trading_thread_pool`
- `maintenance_thread_pool`
- `maintenance_process_pool`

设计要求：

- 交易主链路优先级最高。
- 阻塞 I/O 和 CPU 密集任务必须离开交易主事件循环。
- 持久化和报表不能占用交易执行资源。

## 12. 二次开发入口

按改动归属定位文件：

- 改策略规则：优先改 `src/strategies/current/`
- 改扩展契约：改 `src/polymarket_trader/extension_api/`
- 改交易编排：改 `app/`
- 改接入或存储：改 `infra/`
- 改运行时调度：改 `workers/` 或 `runtime/`
- 改人工查询和操作：改 `api/`

常见错误：

- 在 route 里写交易逻辑。
- 在 worker 里硬编码某个策略阈值。
- 在 domain 层加与当前策略强绑定的字段。
- 为了兼容旧名字在框架层长期保留别名。

## 13. 当前实现说明

仓库已经具备框架化边界，并内置一个示例策略实现。

当前职责分布如下：

- `polymarket_trader.extension_api` 负责业务扩展契约、上下文对象和配置加载。
- `src/strategies/` 负责具体业务扩展差异。
- `main.py` 通过 loader 和 `extension_module` 配置装配运行时。
- worker 和 app service 不直接持有某个具体策略包的业务规则。
